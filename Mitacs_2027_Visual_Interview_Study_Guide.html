Commerce & payments

GCMT Shop

Online store with checkout, orders and invoices.

React · Supabase · PostgreSQL · Vercel · CCAvenue

Workflow Concepts What to say Questions Revision card

Customers browse products, add them to a cart and pay online. Store staff manage the catalog. The hard part is deciding who can set the price and what evidence can change the order to paid.

How it works

  1. React sends shipping and an attempt ID. The server validates the session and reads the caller’s cart.
  2. The server calculates integer paise and saves the item snapshot in a pending order. The browser sends the prepared form to the gateway.
  3. The server checks decrypted fields. SQL locks the matching order, checks the amount and writes the receipt and order/cart changes together. The success screen looks up the caller’s order.
Browser

Starts checkout and shows the saved result.

Trusted path

Server checks identity and price. SQL reconciles the callback.

Encryption and authenticity
Meaning
Encryption hides readable data. Authenticity establishes who sent it.
Why it matters

Project example
The helper uses AES-128-CBC with the provider-style derived key and fixed IV. The handler separately checks response fields against stored data.
What could go wrong
A response that decrypts does not establish that the gateway settled a payment.
Transaction and row lock
Meaning
Commit related changes together and make writers take turns on one order.
Why it matters
Avoid partial changes and conflicting writes.
Project example
Reconciliation locks the order and writes receipt, status and cart effects together.
What could go wrong
Two handlers could otherwise act on the same pending state.
Idempotency
Meaning
Repeating the same operation should leave one effect.
Why it matters
Handle network retries safely.
Project example
A matching receipt replay returns the recorded result.
What could go wrong
Ignoring the contents of a replay could hide a conflicting outcome.

What I can say

20–30 seconds · simple

GCMT is an online shop built with React and Supabase. The part I’d focus on is checkout. The browser starts it, the server works out the real price, and the database records the payment result. That separation matters because anyone can change what their own browser sends.

60–90 seconds · technical

When a customer clicks Pay, the React screen sends shipping details and an attempt ID. The server checks the session, reads that customer’s cart and gets product prices from the database. It calculates the total in paise and saves a pending order with a copy of what was bought. The browser then submits the encrypted request to CCAvenue.

When a response comes back, the server decrypts it, checks the fields and asks the database to match the stored order and amount. A lock and a unique receipt help it handle repeats. The success screen reads the saved order for that user. I’d distinguish this server path from the older Edge Function in my résumé and separate database reconciliation from proof of settlement.

School finance & records

LF Finance Management Software

School fees, accounts and transfers by academic year.

React · TypeScript · Supabase · PostgreSQL

Workflow Concepts What to say Questions Revision card

School staff can see what each student owes and what the school actually received. The app tracks enrollments, fees, transfers, expenses and money to recover. An old fee paid today reduces old debt and increases today’s cash.

How it works

  1. The booking year says when money arrives. The original year identifies older debt, when relevant.
  2. The database checks caller ownership and compares any saved request with the incoming details. An identical retry returns the saved receipt.
  3. A new payment locks the enrollment. Database checks limit the amount. Reports use the saved records to answer both cash and debt questions.
Cash booked now

The current period receives the money.

Debt attached to the original year

The historical enrollment’s unpaid amount falls.

Concepts to understand

Obligation and receipt
Meaning
An obligation is what’s owed. A receipt is money received.
Why it matters
Answer debt and cash questions independently.
Project example
A late receipt can affect today’s cash and a prior enrollment.
What could go wrong
Putting both in one year distorts cash or student debt.
Row-level security (RLS)
Meaning
The database limits which rows a user can access.
Why it matters
Keep financial records isolated at the database boundary.
Project example
Ordinary users are scoped to their own data. Privileged payment functions also check ownership explicitly.
What could go wrong
A caller could submit another owner’s account ID.
Request identity
Meaning
One intended payment gets one stable ID.
Why it matters
Recognize a payment even after a lost reply.
Project example
The function compares the saved details on retry. A unique index backs it up.
What could go wrong
Generating a new ID after a lost reply can turn a retry into a second operation.
Concurrency
Meaning
Two requests can overlap in time.
Why it matters
Protect a shared limit across different requests.
Project example
The enrollment lock makes competing new payments against one obligation take turns.
What could go wrong
Both could read the same balance and overpay it.
Derived balance
Meaning
Calculate a balance from stored movements.
Why it matters
Keep the balance tied to a record of real movements.
Project example
A single transfer reduces one account and increases the other.
What could go wrong
Treating a transfer as income inflates the school’s overall funds.

What I can say

20–30 seconds · simple

LF Finance helps a school manage fees and accounts across academic years. The central idea is that a student’s debt and a receipt are different records. If someone pays last year’s fee today, it reduces that old balance while the money arrives in the current year.

60–90 seconds · technical

React collects the receipt details and sends them through a service to a Supabase database function. The receipt can name the year money came in and the earlier year whose fee is being paid. The function checks that the caller owns the related records.

It looks for the same request ID before doing new work, then locks the enrollment to check what can still be paid. This matters because the same request can be retried, while two different requests can compete for the same unpaid amount. Transfers are stored as one movement between two accounts. I’d also point out that the steps to create historical records and the actual payment call are separate.

Property search & publishing

UrbanEdge Land Space

Property search with private intake and controlled publication.

Next.js · React · TypeScript · PostgreSQL · Supabase

Workflow Concepts What to say Questions Revision card

Visitors search for listings and can request help or a visit. Owners can submit properties for review. Staff manage leads, visits and the decision to publish, while public screens receive a smaller set of fields.

How it works

  2. The server builds each card from allowed fields. Private inputs used to review a listing stay in a separate workflow.
  3. On the staff path, an active admin reviews readiness and requests publication. The principal database path groups changes. The fallback has separate calls.

Patterns that transfer between projects

  • Trust the right layer. A hidden button or displayed total is easy to bypass. Check permissions and price at the trusted boundary.
  • Give retries an identity. Reuse one request ID. Check both whether it exists and whether the details match.
  • Group changes that belong together. Trace exactly which writes share a transaction. External effects and earlier requests can survive a local failure.
  • Protect shared state. A lock coordinates competing writes to one record. A unique key protects a specific identity.
  • Measure the claim you make. Separate source, an executed check and live behavior. Characters, tokens and task success are different measurements.
